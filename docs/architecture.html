The big picture

Grimoire is a D&D character manager — character sheets, a homebrew content authoring studio, a searchable library of official rules content, and a "Live Play" mode where a DM runs a fight and players' phones join over the local network. This repository (the phone/browser app) is the original. A separate repository holds a native C++20 / Qt 6 desktop port of the same engine, re-implementing the same rules so they run natively on Windows/Linux/macOS, while staying able to read and write the exact same character files and homebrew packs this app produces. This page documents that port's codebase.

That porting relationship is visible everywhere in the C++ code: nearly every file's opening comment names the exact TypeScript file it ports (src/engine/leveling.ts, combat.ts, and so on, all in this repository). Treat those comments as the most reliable map there is — when a ported function's behavior is unclear, the comment usually says which original file defined that behavior first.

The C++ port has three layers, and they don't overlap:

Layer 1 — The enginecore/ — pure C++20, zero Qt, zero UI. All rules logic: computing stats, resolving effects, applying damage, leveling up, compiling homebrew drafts, running a fight. Operates entirely on plain JSON, not custom classes.
Layer 2 — View-modelsui/*.cpp — the Qt/QML bridge. Thin classes exposing the engine's state and actions to the UI as Qt properties and invokable methods. No rules logic lives here.
Layer 3 — The UIui/qml/*.qml — every pixel on screen: pages, dialogs, small reusable components, in Qt's declarative QML language.

Why this separation matters: core/ can be (and is) compiled and unit-tested completely on its own, with no Qt installed at all. The UI is an optional add-on layered on top (GRIMOIRE_BUILD_UI in CMake). If you're trying to understand a rule of the game, you almost certainly want core/, not ui/.

The one idea that explains everything

If you remember nothing else, remember this: a character is not a C++ object — it is a JSON tree, and the engine mutates that tree directly.

Every character, every homebrew draft, every monster — all of it is nlohmann::ordered_json (an ordered-keys JSON library), aliased throughout as OrderedJson. There's no Character class with a strength field. Instead, a function like recomputeDerived(entity, &catalog) takes a reference to the raw JSON object, reads fields out of it by string key (entity["abilityScores"]["str"]), and either returns a computed result or writes new fields back into the same object in place.

This is a deliberate consequence of the porting relationship: this app is written in TypeScript, where a character is just a plain JS object serialized to JSON. Porting that design 1:1 — rather than inventing a typed C++ domain model — means a character file this app wrote opens correctly in the desktop app and vice versa, and a porting bug shows up as "this field is wrong" rather than "this doesn't compile," which is far easier to diff against the original.

The practical upshot: to find where a field like "proficiencyBonus" or "turnState" comes from, you grep for the literal string key across core/ — there's no type definition to jump to. Almost every file in core/rules/ has a cluster of tiny helpers near its top (str(), num(), arr(), obj(), member(), truthy()) that safely pull a typed value out of an OrderedJson by key, tolerating a missing or wrong-shaped field instead of throwing.

One exception worth knowing up front: core/model/ contains an earlier, abandoned attempt at a strongly-typed C++ domain model (a real Entity, Feature, Resource class). It was the very first design, kept for one historical demo program, and nothing else in the codebase depends on it. See Legacy corners.

The container for all of this is CharacterDocument (core/io/CharacterDocument.h) — a thin wrapper around one OrderedJson holding the exact envelope both apps exchange: {"format":"grimoire-character","version":1, "exportedAt":…,"entity":{…}}. Its defining rule: the native engine reads and edits only the fields it understands, at any depth, and carries everything else through untouched on save — so opening a character in the desktop port and saving it again never silently deletes a field this app wrote that the port hasn't learned about yet.

A rule of thumb that holds almost everywhere: if it's about what a character can do, it's in core/rules/. If it's about turning what a person typed into something the engine can run, it's in core/homebrew/. If it's a widget on screen, it's in ui/qml/.

The core engine — core/rules/

Twenty-two files, no two of them doing the same job. This is the heart of the application. Every file here is small enough to read in one sitting and owns exactly one slice of the rules. None of them know anything about Qt, QML, SQLite, or the network — they take an OrderedJson& (almost always the character's entity), read and mutate it, and sometimes take a const ItemCatalog* (the loaded rules content) and/or a Rng& (a seeded random source, for anything that rolls dice). Deep dive: how a character's stats actually get computed

core/rules/EffectPipeline.cpp — 1,364 lines, the single most important file to understand if you're debugging "why is this number wrong."

Nothing about a character's stats is stored pre-computed. Armor Class, proficiency bonus, every saving throw, spell save DC, passive Perception — none of it lives in the JSON as a settled number. Instead, one function, recomputeDerived(character, items), is called fresh every time anything might have changed, and it rebuilds all of it from scratch:

  1. Collect every effect. Walks every granted feature — class features, species traits, feats, item effects, active conditions — and gathers every typed effect each one carries.
  2. Fold them together. Effects targeting the same stat combine by their declared operation (mostly addition; some "set" and "advantage/disadvantage" effects don't stack numerically).
  3. Apply any active Free Edit override last. A map, overrideByStat, is built from every active entry in entity["characterOverrides"] / ["dmOverrides"]. Each stat's computation calls withOverride(naturalValue, statName), which replaces or adds to the natural value and marks the override claimed. Anything left unclaimed is reported as unsupported rather than silently doing nothing.
  4. Return a NativeDerived struct — every computed stat, plus an explainability trail so the sheet can show the breakdown, not just the final number.

Nothing here writes to the character. recomputeDerived is read-only — it's reconcileEntity() in Rest.cpp that calls it and then writes a handful of the results back (current/max HP, a few resource pools) into the stored JSON. Everything else (AC, saves, DCs) is never stored — it's recomputed on every read, every time.

If you're adding a new kind of stat modifier, or tracing why a bonus isn't applying, this file's big dispatch over effect type strings is where that logic lives.

Three mechanisms worth knowing by name

Rest.cpp's reconcileEntity() — the "settle everything" chokepoint

Almost every function that changes a character ends with a call to reconcileEntity(character, items). It calls recomputeDerived() for fresh numbers, resyncs resource-pool maxima against any upgrade entitlement, applies the HP-bonus delta and a few formula-linked pool resyncs, toggles an "activate at X% HP" condition on or off, and — last, so it always has final say — resolves any active Free Edit override of a custom resource pool's current/max. New "resync this after every change" logic almost always gets added as one more small pass inside this one function, near the end.

Cards.cpp — the action economy

A "card" is the engine's name for one usable thing on the sheet — a spell, a limited-use class feature, an item's activated ability. generateActionCards() builds the full list; useActionCard() checks legality (resource available, right action-economy slot free), applies the effect, marks the slot used, and reconciles. The action economy tracks three standard slots on entity["turnState"] (action/bonus action/reaction) plus an open-ended turnState.custom map for any homebrew-authored named slot. A fresh turn clears all of it via resetTurnEconomy().

Choices.cpp — "pick N of these"

Every "choose 2 skills," "choose a Fighting Style," "choose an Eldritch Invocation" moment goes through one generic mechanism: a prompt, a pool of options, a count. Resolving one can itself grant more features. Options can declare prerequisites on each other ({kind: "has_option", optionId: …}) or on level — the same machinery official content uses, and, as of the port's own recent work, authorable from the homebrew builder too.

The homebrew compiler — core/homebrew/

Draft (what a person typed) → compiled record (what the engine runs) → validation (is it legal). This is the second-largest subsystem and arguably the most distinctive part of the whole app: ordinary players author their own species, classes, spells, items, and monsters through a guided builder, and that content runs through exactly the same engine code as official SRD content — there's no separate "homebrew mode" in the rules logic. Homebrew.cpp is what makes that true: a pure, stateless compiler.

FileJob
Homebrew.cppThe compiler itself: one function per content kind (compileFeatFields, compileSpellFields, compileSubclassFields, …) plus the validators that decide whether a draft is acceptable to save.
HomebrewLibrary.h/.cppThe SQLite-backed store of a person's own saved homebrew (HomebrewStore) — separate from the character database. See "Persistence".

The trait system — one editor for every kind of mechanical effect

Almost everything a homebrew author builds — a feat's effect, an item's power, a condition's consequence, one level of a class — bottoms out in the same shape: a trait draft, edited by one shared QML component (TraitEditor.qml) and compiled by one shared function, buildTraitFeature(). A trait draft is a flat bag of fields, and the compiler reads out whichever fields its effectKind actually uses. Adding a genuinely new capability almost always means: one new field on the trait draft, a UI control for it, and a few lines in buildTraitFeature() (or its helper layerAdvanced()) to compile that field into a real effect.

Nearly everything is a free string, by design. Damage types, recharge cadences, condition ids, action-economy slot names — almost none of these are validated against a closed enum anywhere in core/. A closed list you still find is almost always a UI choice (a fixed set of Chips in a QML file) layered on top of a field the compiler already accepts as free text. When extending a vocabulary, check the compiler's own tolerance first — it's very often already general.

Content & packs — core/content/

A "pack" is a signed JSON file holding a complete ruleset's worth of content. Two ship with the app (SRD 5.1 and SRD 5.2.1, in content/packs/); a person can install more, and their own homebrew behaves like a third, always-installed pack layered on top.

FileJob
Items.h/.cppThe big one: ItemCatalog, holding every loaded pack's content in memory and answering lookups — findSpell, findClass, findSubclass, spellsFor(ruleset). Each content kind is looked up its own way; there is no single generic "find any record" method baked in — findBrowsable() is a newer addition that dispatches across all of them for exactly that purpose.
Registries.h/.cppThe flat reference lists a choice can draw from: every tool, language, skill.
ContentRegistry.h/.cppA minimal definition/instance lookup for the earlier typed model — mostly historical now.

Two more pieces matter here: core/io/PackVerifier.h checks a pack's Ed25519 signature (via the Monocypher library) before anything in it is trusted, and core/io/Sha256.h computes the content hash recorded in a pack's manifest.

On the UI side, ContentService (ui/ContentService.h) is the single shared owner of both the loaded ItemCatalog and the open HomebrewStore — a Meyers singleton (ContentService::instance()), constructed once, read by every view-model.

Persistence — two separate SQLite files, deliberately

There is no single "the database." Two completely separate SQLite stores, matching the fact that characters and homebrew content have different lifetimes and sharing models:

core/storage/CharacterStore.h/.cpp
The person's own characters. Deliberately never shared with this app — the two apps exchange characters as files, not through a shared database.
core/homebrew/HomebrewLibrary.h's HomebrewStore
The person's own saved homebrew — kept once, loaded into the in-memory ItemCatalog at startup and reloaded after any save/import.

The shared trait-editing components

These four files are reused across almost every builder, which is why a fix to one of them tends to fix the same problem everywhere at once: TraitEditor.qml (the main effect editor), TraitAdvanced.qml (riders, auras, HP-threshold activation), LevelFeatures.qml (a features-by-level list), and ChoiceList.qml (feature pools and their options).

One non-obvious wrinkle worth knowing before touching any of these: a QML Repeater bound to a plain JavaScript array has no identity tracking between items — reassigning the array destroys and recreates every delegate, including whichever one has keyboard focus. Every list-editing file handles this the same way: buffer an edit, debounce the real array reassignment behind a short Timer, and expose a synchronous flushPending…() called before anything that reads the "real" state directly. Copy this pattern for new list-editing controls.

Worked example: clicking "Damage" on the sheet

A pure core function: reads resistances/immunities/vulnerabilities, computes the real amount, writes resources.hp.current straight into the JSON.

5

Worked example: saving a homebrew feat

1
ui/qml/HomebrewPage.qml
Saving flushes any pending edit, then calls homebrew.save(editType, draft, editId).
2
ui/HomebrewViewModel.cpp — save()
Converts the draft to OrderedJson, calls compileFeatFields(draft, id) in Homebrew.cpp.
3
core/homebrew/Homebrew.cpp
Produces the same compiled JSON shape an official feat record has, then validates it.
4
ui/HomebrewViewModel.cpp
If valid: writes the compiled record into HomebrewStore, and separately preserves the original draft in the record's own homebrewDraft field for re-editing later.
5
ui/ContentService.cpp — reloadHomebrew()
The shared catalog re-reads the library, so the new feat is immediately visible everywhere.

This is also exactly how official and homebrew content end up running through identical code at play time: once compiled, nothing downstream can tell whether a feature came from the bundled SRD pack or from someone's own draft typed five minutes ago.

Testing & verification strategy

Core unit tests — tests/*.cpp, 23 files

Built as grimoire_tests (Catch2), linking only grimoire_core — no Qt. Named by subsystem, using 344 small synthetic character fixtures as starting states.

Parity tests — tests/test_parity.cpp

The most distinctive check in the project: a generated golden file — over a million lines, tens of thousands of cases — each recording an operation and the exact JSON this app's own engine produced for it. The C++ test runs the same operation natively and diffs byte-for-byte against that golden output. This is the port's real confidence that it behaves identically to the original, not just "looks about right."

UI tests — ui/tests/*.cpp

A second Catch2 executable, grimoire_ui_tests, instantiating the real view-models against a throwaway in-memory database and driving them exactly the way QML would.

The compliance/traceability system — docs/compliance/

A document-level layer above the test suites: a contract document stating every rule the app must hold, each with a stable id; a requirements file linking specific test cases as evidence for specific rules; and a generated report that refuses to call a requirement "verified" unless its linked evidence actually ran and passed in that exact run.

Patterns worth recognizing on sight

Free Edit / Override — "set" vs. "add"

A DM correction is stored as a labeled record with a stat (a free string, e.g. "ac" or "resource.blood_debt.maximum"), an operation ("set" replaces the natural value; "add" adds a delta on top), and a value. For an ordinary derived stat, "add" is naturally stable because the natural value is recomputed fresh every time. For a stored resource pool it isn't — so an "add" there is resolved once and the stored override rewritten into an equivalent "set," a one-time correction rather than something that silently keeps compounding on every reopen.

"Is this field validated anywhere?" — usually no, by design

The default is a free string with no enum-style validation. A closed list almost always lives purely in a QML Chips control, not in the compiler. Before assuming you need to loosen validation, check whether the core already accepts the value and the real gap is only that nothing in the UI lets someone type past the preset options.

Comments that name the TypeScript original

Nearly every file in core/ opens with a comment naming the exact src/engine/*.ts or src/content/*.ts file (in this repository) it ports. When behavior looks surprising, that's usually the fastest way to find out whether it's intentional or a porting gap.

Legacy corners — what not to build on

Two parts of the C++ port are historical and not part of how the real app works today.

core/model/abandonedA strongly-typed C++ domain model — the project's very first design, before the current JSON-everywhere approach. Only Entity.cpp (26 lines) still compiles, and nothing else depends on it.
app/main.cpphistorical demoA small CLI program building one hardcoded "Human Fighter, Level 1" on the old typed model. The project's first-ever commit, kept as a build target but not the real application — that's ui/main.cpp.
