The one idea: everything is an Entity

Player characters, monsters and NPCs are the same type, run through the same engine. Combat, conditions and stat logic are written once. An abridged version of src/engine/types.ts:

type Entity = {
  id: string;
  kind: 'character' | 'monster' | 'npc';
  identity: Identity;            // name, level, class, species, ruleset
  stats: AbilityScores;          // the six scores as assigned
  derived: DerivedStats;         // AC, saves, skills, passives, spell DC: always computed
  resources: ResourceBlock;      // HP, hit dice, spell slots, feature pools
  inventory: InventoryBlock;
  conditions: ActiveCondition[];
  features: FeatureInstance[];   // every trait, class feature, feat and item power
  choices: ChoiceState[];        // decisions still owed: skills, a subclass, a feat or ASI
  dmOverrides: DmOverride[];
  // ...
};

The interesting part is features. A racial trait, a class feature, a feat, a magic item's property, a condition and a piece of homebrew all reduce to the same Feature:

  • Effects are passive and typed: a target, an operation (add, set, multiply, scale, advantage, resistance and so on), a value and an optional condition.
  • Actions become action cards: attacks, spells, activatable abilities and their costs.
  • Choices are decisions the feature asks of the player, resolved through the same code in the creation wizard and at level-up.
// "+1 to AC", from a feat, an item or homebrew alike
{ type: 'stat_modifier', target: 'ac', operation: 'add', value: 1, condition: null }

Because content is data rather than code, the engine has almost no per-class branches. There is no scripting language either: homebrew is built from the same typed pieces, so a shared file can always be inspected and validated before it runs.

How a number gets computed

What happens when a player equips a shield:

  1. 1app/sheet/[id].tsx → src/store/characterStore.tsThe screen calls updateCharacter(id, updater, label). Screens never compute rules themselves.
  2. 2src/engine/*.tsThe updater calls engine functions that take an Entity and return a new Entity. Nothing is mutated in place.
  3. 3src/engine/pipeline.ts: recomputeDerived(entity, rules)Collects every active effect from features, equipped items, conditions and overrides, resolves them per target (bonuses stack, set picks a winner, scale applies last), and rebuilds derived and the action cards.
  4. 4src/store/characterStore.tsThe store pushes an undo entry, schedules a save to SQLite, writes a timeline entry and sends a patch to any live-session peers.
  5. 5src/engine/audit.ts: explainValue(entity, stat)When the player taps AC, the same contributions are rebuilt as a list of labelled entries. The "why" screen and the number come from the same effects.

Campaign rules (point buy, level caps, rest lengths, crit rules) arrive as a CampaignRules value passed into the engine, not as global switches, which is why one device can hold characters under different house rules.

Content packs and signatures

Official content reaches characters through content packs: JSON files with a manifest, the records (classes, species, spells, items, monsters and so on) and rules tables. The two SRD packs are built from the source data in src/content/, ship in assets/packs/ and are installed on first launch. A .grimoire-pack of homebrew uses the same envelope.

  • Content hash. contentHash is SHA-256 over the canonical JSON (keys sorted, undefined dropped) of the pack's records and rules.
  • Signature. Ed25519 over "grimoire-pack-signature-v1\n" + canonicalJson(manifest without signature). The manifest includes the hash, so one signature covers the whole pack. Trusted public keys are in src/content/trustedKeys.ts.
  • Install order (src/content/officialPackService.ts): envelope, manifest, content hash, record validation, signature, dependency resolution, then activation. A forged signature is always refused. An unsigned or unknown-key pack needs the user's explicit confirmation. The bundled packs must be validly signed.
  • Resolution. The content provider (src/content/provider/) merges installed packs by id, and the user's homebrew wins over a pack record with the same id.

Packs are rebuilt with npx tsx scripts/build-srd-packs.ts. Without the private signing key, which is not in the repository, a rebuilt pack whose content is unchanged keeps its committed signature.

Storage

One SQLite database per install. Characters, campaigns and homebrew are stored as JSON documents in a few tables rather than spread across a relational schema, so the domain model can grow without table rewrites. Tables include entities, campaigns, content_cache (homebrew) and its content_cache_history, character_timeline, installed_packs, official_packs, prepared_encounters, combat_state and custom_rule_profiles. Tables are created with CREATE TABLE IF NOT EXISTS at start-up (src/db/db.ts).

In the browser, expo-sqlite runs as WebAssembly with a file in the browser's private storage. That needs a cross-origin-isolated page, and GitHub Pages cannot send the headers, so a small service worker (scripts/web/coi-sw.js) adds them.

Live play over the LAN

Live play is direct device-to-device TCP on the local network. Messages are newline-delimited JSON. A room code is the host's IPv4 address written as 7 characters from a 32-character alphabet without 0, O, 1, I or L, so it is a convenience, not a secret.

Two layers exist side by side:

  • src/session/ (port 7743). SessionHost is the authoritative state machine. Participants hold capabilities (host, dm, player), each authenticated by a per-participant token, and every operation is checked against them. Each viewer receives a projection of the state built for them, so DM-only data never reaches a player's device. A DM's change to the character itself (dm.request_change) is a request the player accepts, edits or declines, while fight consequences on the tracker, such as hit points and conditions, the DM applies directly. Transports are pluggable: in-memory and loopback ones drive the tests.
  • src/sync/ (port 7742). The older campaign sync, where the device that created the campaign is both host and DM, and entity patches are relayed between devices.

Neither layer encrypts traffic yet, so live play is for networks you trust. scripts/e2e/ runs real sessions against a phone over adb, with a Node "table" playing the other seats and a proxy that cuts the link on demand.

Android, browser and desktop

  • Android is the main build, released as a signed APK on GitHub Releases.
  • Browser. expo export --platform web, finished by scripts/web/finish-web-export.js (service worker, fallback for deep links) and published in docs/app/. GRIMOIRE_WEB_BASE_URL sets the sub-path. No live play there, because a web page cannot open TCP sockets.
  • Desktop. desktop/ loads the same web build in Electron through a grimoire:// scheme that adds the isolation headers and a content security policy. It gives the page real TCP sockets through a narrow IPC bridge that checks the caller is the app's own page, and metro.config.js swaps react-native-tcp-socket for a shim over that bridge, so the live-session code can run there. In the current source the live-session buttons are still hidden on every web build, the desktop one included (src/platform/features.ts). It is built from source for Windows; there is no desktop release yet.

Build, run, test

git clone https://github.com/nkvanch/Grimoire.git
cd Grimoire
npm install          # also applies the patches in patches/
npx expo start       # then open it on a device, an emulator or the web
npm test             # Jest: about 3,500 tests, a couple of minutes
npm run typecheck    # tsc --noEmit
npm run lint         # ESLint with typed rules

Good first files to read, in this order:

  1. src/engine/types.ts: Entity, Feature, Effect, Choice.
  2. src/engine/pipeline.ts: recomputeDerived.
  3. src/engine/audit.ts: how the "why" lists are built.
  4. src/store/characterStore.ts: updateCharacter, undo and redo.
  5. src/content/officialPackService.ts and src/content/packSigning.ts.
  6. src/session/host.ts: roles, operations and projections.

Rough edges

Honest notes for anyone about to read the code:

  • There is no CI yet. Type-check and tests pass on main; npm run lint still reports errors.
  • The engine is meant to be pure, but a few engine files import constants from src/store/. Do not copy that pattern.
  • The release scripts (APK build, Maestro runs) are PowerShell and assume Windows.
  • Two live-play layers exist, as described above.
  • Many files carry long comments that name past audit findings. They explain why code looks the way it does, so read them before "simplifying".
  • The database has no schema version yet. Changes are additive, and older saved data is upgraded when it loads.
