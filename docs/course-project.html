1. The problem

In a tabletop role-playing game such as Dungeons & Dragons, every player keeps a character sheet. It looks like a form, but it behaves like a program: most of its numbers are calculated from rules and from other numbers. Put on chain mail and a shield, and armor class goes from 11 to 18 and stealth gets disadvantage. On paper, players redo that math by hand, and mistakes are common.

Most digital tools for these games need an account and an internet connection, or are virtual tabletops built for playing online. Few are made for people sitting at the same table.

2. The idea

Treat the game rules as data and the sheet as a program that runs them.

Offline and privateCharacters live in a SQLite database on the device. No account, no server, no tracking.
Every number explains itselfTap armor class and see its parts: chain mail 16, shield +2.
Play together at the tableThe game master’s phone hosts a live session that players join over the same Wi-Fi.

The work splits into four areas: product and rules design (features, scope, rules accuracy, licensing), the engine and data (character model, rules pipeline, content packs), the interface (creation, sheet, game-master tools, this website), and testing and releases.

The project was built with an AI pair programmer (Claude). The team set the direction, checked the rules against the source documents, reviewed and tested every change on real devices, and made every release. The commit history on GitHub records each step.

5. Method

  • Release often. Five alpha releases in three weeks, each with a public changelog, and a feedback page for testers.
  • Principles in writing. Game mechanics are data, not code, and the app never pretends to automate something it does not. See the rules it is built on.
  • A pure rules engine. The rules are plain functions with no screen code, so each one can be tested on its own. The suite has 3,558 tests, all passing.
  • Checks on every push. GitHub Actions runs type checking, the linter and every test.

Stack: TypeScript, React Native with Expo, SQLite, Zustand, Jest, GitHub Actions, GitHub Pages, Electron. The developer guide explains the code in depth.

6. How it works: one tap

  • 1The player taps Equip on chain mail. The screen does no math.app/sheet/[id].tsx
  • 2The rules engine recalculates the character: armor class, hit points and attacks are derived from source data every time, never stored.src/engine/pipeline.ts · recomputeDerived()
  • 3One store holds the result, and every screen reads it.src/store/characterStore.ts
  • 4It is saved to SQLite on the device at once, so it works offline.src/db
  • 5In a live session it goes to the other phones as JSON messages, one per line, over TCP on the local network. The host phone is the authority and sends each person only what they may see.src/session · port 7743

8. Evidence: real code

Content packs must arrive exactly as published. Two JSON files with the same content can differ in key order, so the app first turns content into one canonical text. The function is recursive: it calls itself for every nested list and object, and it sorts each object’s keys.

/** Canonical JSON: object keys sorted and undefined members dropped, so the same content always hashes the same. */
export function canonicalJson(value: unknown): string {
  if (Array.isArray(value)) return `[${value.map(canonicalJson).join(',')}]`;
  if (value && typeof value === 'object') {
    const o = value as Record<string, unknown>;
    return `{${Object.keys(o).filter(k => o[k] !== undefined).sort().map(k => `${JSON.stringify(k)}:${canonicalJson(o[k])}`).join(',')}}`;
  }
  return JSON.stringify(value);
}

The app then takes the SHA-256 hash of that text and refuses a pack whose hash differs from the fingerprint in its manifest, which is signed with Ed25519. Source: contentPackManifest.ts and officialPackService.ts.

10. Challenges

  • A feature that only looked done. Rage showed its card and spent its use, but its effect never reached the character. Now every Use runs the ability’s effects. The lesson: test the change in the data, not the screen.
  • Licensing is part of the specification. We assumed the System Reference Document has every feat and background; it has one of each. A test now compares our text with the SRD itself.
  • Two ways to host a game. An older sync system lived beside the new live session, and the two could disagree. The old one was removed: one Host button, one protocol.
  • A database inside a browser. SQLite in the browser needs cross-origin isolation, which GitHub Pages does not switch on. A small service worker adds it.

11. Limits and next steps

  • Live play is not encrypted yet: fine on a home network, not on public Wi-Fi.
  • On phones it runs on Android only.
  • Found while preparing the presentation: the 2014 Champion’s critical hit on 19–20 is described but not yet applied. The engine supports it; the signed content pack needs a fix.

Next: encrypt the live session, fix and re-sign the 2014 pack, then version 1.0.
